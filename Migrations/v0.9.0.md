# Migration Guide: Geurts Documentation v0.9.0

**Version:** 0.9.0
**Status:** Non-normative migration guide
**Required package path:** `Migrations/v0.9.0.md`

## Purpose

This guide records the planned transition from the former three-visible-entry installation to package v0.9.0. It is a checklist and target-release snapshot, not an integration, subject, or conflict authority.

For current requirements, follow `GeurtsTechniqueManifest.md`. It selects:

- `GeurtsTechniques/GeurtsGameForgeIntelligenceTechnique.md` for the Game Forge Intelligence documentation-consumption and compatibility boundary;
- `GeurtsTechniques/GeurtsAIAgentSetupTechnique.md` for Geurts-owned native entries and safe managed-region edits;
- `GeurtsTechniques/GeurtsFolderStructureTechnique.md` and its JSON Definition for folder meaning and folder-tool scope;
- `GeurtsTechniques/GeurtsGameDesignDocumentationTechnique.md` for GDD discovery and explicit maintenance boundaries; and
- `GeurtsTechniques/GeurtsGitIgnoreTechnique.md` for the project-root `.gitignore` payload and preservation contract.

If this guide differs from a selected normative technique, the technique governs.

## Migration Checklist

1. Commit or otherwise back up the Unity project.
2. Install a Game Forge Intelligence version that declares support for the selected v1.0.0 Technique and compatibility schema.
3. Confirm that possible user-authored changes in the previous documentation copy, native entries, GDD, and `.gitignore` are identified before migration. A migration does not authorize silent replacement.
4. Use the conforming migration owned by Game Forge Intelligence and defined by its selected technique. Do not overlay the new tree onto the former three-entry folder file by file.
5. Confirm the installed content conforms to the selected Game Forge Intelligence Technique rather than the former visible-entry allowlist.
6. Confirm plugin reading starts through copied `AGENTS.md` and the manifest-controlled chain described by the active manifest and Game Forge Intelligence Technique.
7. Migrate only supported native entries through their actual owner. The generic manager owns Geurts markers/templates; product-owned or unrecognized legacy material remains outside that workflow. Preserve unknown, modified, or user-authored content.
8. Keep GDD scaffolding and GDD manifest maintenance as separate explicit user opt-ins. Do not invent project design facts.
9. Apply the Git Ignore Technique only with its required explicit authorization. Preserve a differing project-root `.gitignore` and Git index state.
10. Validate using the current repository automation suite and static validator on Windows PowerShell 5.1 and PowerShell 7 where available; do not rely on historical pass counts.

## Manual Geurts Entry and GDD Opt-Ins

The default manager invocation changes supported Geurts native entries only. These examples are independent explicit operations and always name the Unity project root:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<ProjectRoot>/GeurtsGameForgeDocumentation/Tools/ManageGeurtsAgentInstructions.ps1" -ProjectRoot "<ProjectRoot>"
powershell -NoProfile -ExecutionPolicy Bypass -File "<ProjectRoot>/GeurtsGameForgeDocumentation/Tools/ManageGeurtsAgentInstructions.ps1" -ProjectRoot "<ProjectRoot>" -IncludeGameDesignScaffolding
powershell -NoProfile -ExecutionPolicy Bypass -File "<ProjectRoot>/GeurtsGameForgeDocumentation/Tools/ManageGeurtsAgentInstructions.ps1" -ProjectRoot "<ProjectRoot>" -UpdateGameDesignManifest
```

The first operation changes no GDD content. The second creates only missing GDD scaffolds. The third requests deterministic manifest maintenance. Existing project-authored content remains governed by the Setup and GDD Techniques.
