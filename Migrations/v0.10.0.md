# Migration Guide: Geurts Documentation v0.10.0

**Version:** 0.10.0
**Status:** Non-normative superseded transition guide
**Required package path:** `Migrations/v0.10.0.md`

## Purpose

This guide records the superseded planned transition to package v0.10.0 and Game Forge Intelligence compatibility schema 2.0.0. It is historical context, not an integration, subject, conflict authority, or current checklist. Use `Migrations/v0.11.0.md` for the current transition, and follow `GeurtsTechniqueManifest.md`, which assigns current documentation setup and Update exclusively to the Documentation Companion.

Nothing below authorizes current updater behavior. The remaining text preserves the v0.10.0 proposal only so released-consumer compatibility can be assessed.

## Target Boundary

`Geurtsy/GeurtsGameForge_Documentation` on `main` is the sole source and authority for all Geurts Game Forge documentation. Game Forge Intelligence owns only its notification metadata check, explicit Update implementation, and consumption of the detached project-local fetched copy:

```text
<ProjectRoot>/GeurtsGameForgeDocumentation/
```

The `com.gameforge.intelligence` Unity package contains only plugin-specific documentation under its own `Documentation~`. Those plugin documents may reference this repository but may not embed, duplicate, redefine, or become authority for Geurts documentation.

Project-authored design remains separate and byte-preserved at:

```text
<ProjectRoot>/Docs/GameDesign/
```

## Behavioural Change from v0.9.0

Each normal Unity launch/open now performs exactly one lightweight metadata check against the authoritative repository's `main` branch. When the exact destination exists, it notifies only when the remote head commit ID differs from the authoritative selected commit ID in the current installed receipt. Package version is display-only and never determines availability. If the remote commit is unavailable, the destination is absent, or there is no valid installed commit ID, availability is unknown and must not be inferred from local bytes or package-version comparison. The check does not download documentation, inspect the local copy, install or synchronize files, mutate the project, recover content, or reintegrate anything. It is non-blocking, and ordinary AI/session initialization performs no additional remote check. A missing copy remains unavailable until the user explicitly selects `Update Geurts Game Forge Documentation`.

The current installed receipt remains outside the fetched copy. Every successful Update records the authoritative selected commit ID and also records the authoritative package version when valid. The receipt is not a Git connection, local-drift ledger, backup, recovery gate, or authority, and local edits do not affect update availability.

The Geurts Documentation UI shows `Installed Geurts Documentation` from the valid package version in the current installed receipt and `GameForgeIntelligence Plugin` from canonical Unity package metadata. It never derives either value from mutable local documentation bytes. A known missing destination shows `Not installed`; an existing copy without a trustworthy current receipt and valid package version shows `Unknown`; unavailable or invalid canonical plugin metadata shows plugin version `Unknown`. When commit-ID inequality establishes availability, the notification shows `Available Geurts Documentation` if the bounded remote lookup supplies a valid version, or `Update available (version unknown)` otherwise. Integration Technique and Compatibility Schema versions remain separately labelled diagnostic values.

The confirmed Update deletes and replaces only `GeurtsGameForgeDocumentation`. Immediately before destructive live deletion, it invalidates the current installed receipt. A historical receipt must never drive the installed label or availability comparison afterward, and the new receipt is written only after complete success. If failure or interruption then leaves the destination absent, the UI shows `Not installed`; if any incomplete directory exists, it shows `Unknown`. These display rules are not recovery state and never block another explicit Update.

The replacement is a detached writable snapshot with no `.git` metadata, repository/worktree/remote connection, or acquisition-preserved read-only attributes. Users may edit it, but every local edit inside it is intentionally discarded by the next confirmed Update.

The old stateful launch checker/downloader, activation transaction, snapshot, rollback, journal, recovery gate, quarantine, last-valid state, local-drift preservation/override, reintegration state machine, blocking backup/recovery state, and plugin-managed legacy installer migration are removed. The new notification-only metadata request does not revive them. Ephemeral acquisition after confirmation is permitted, but cleanup is best-effort and residue never blocks another Update.

The Folder Structure Technique and its machine-readable definition advance together to v0.9.0 so the fetched-copy placement is described as detached and writable rather than read-only or synchronized. The 69-entry registry and 67-path project profile are unchanged; both consuming tools reject an older or mismatched definition before project mutation.

## Migration Checklist

1. For this one-time contract transition, use a Game Forge Intelligence build that implements compatibility schema 2.0.0. Once implemented, later Geurts documentation releases remain independently versioned and do not require a plugin release.
2. Remove any bundled or duplicated Geurts technique content from `com.gameforge.intelligence`; retain only plugin-specific documentation under its `Documentation~`.
3. On project launch/open, perform only the single non-blocking remote-head commit-ID comparison and availability notification. Treat package version as display-only and treat a missing valid installed commit ID as unknown. Do not inspect local files or start download, installation, synchronization, recovery, reintegration, or mutation; do not repeat the check for ordinary AI/session initialization.
4. Verify every successful Update receipt records the selected commit ID plus the authoritative package version when valid, and verify the UI labels installed Geurts documentation and the GameForgeIntelligence plugin separately using their prescribed metadata sources and explicit `Not installed`/`Unknown` states.
5. If local edits inside `GeurtsGameForgeDocumentation` must be retained for reference, the user may copy them elsewhere before Update. The plugin does not detect, preserve, merge, back up, or request an override for them.
6. Explicitly select `Update Geurts Game Forge Documentation` and review the cancel-default destructive warning.
7. After confirmation, expect only `GeurtsGameForgeDocumentation` to be deleted and replaced from the current complete Git-tracked tree on official `main`.
8. Verify the current installed receipt is invalidated immediately before live deletion, cannot fall back to historical metadata, and is rewritten only after complete success.
9. Confirm the result is a writable detached snapshot containing no Git metadata or continuing source connection.
10. Confirm `Docs/GameDesign`, project-root native entries, project folders, a differing `.gitignore`, and every other project file are unchanged.
11. If replacement fails or is interrupted, accept that the fetched copy may be missing or incomplete and that its installed label is respectively `Not installed` or `Unknown`. Correct the external cause and explicitly run Update again; there is no rollback or reset-recovery flow.
12. Leave legacy evidence under `Library/GameForgeIntelligence/` untouched. It is outside the new lifecycle and must never block normal use or Update.
13. Confirm the Folder Structure Technique, definition, creator, and native manager all use definition v0.9.0; this is a contract-version alignment, not a request to recreate or delete project folders.

## Generic Tool Boundary

Documentation Update does not invoke `ManageGeurtsAgentInstructions.ps1`, `CreateGeurtsFolderStructure.ps1`, or `UpdateGameDesignManifest.ps1`. Native entries, GDD scaffolding, bounded GDD manifest maintenance, folder creation, and `.gitignore` provisioning remain independent operations with their own explicit authorization and preservation contracts.

The lifecycle simplification does not weaken generic safeguards. Tools still must not invent project-specific GDD facts, overwrite project-authored GDD, silently overwrite user-authored native entries, or alter a differing project-root `.gitignore`.
