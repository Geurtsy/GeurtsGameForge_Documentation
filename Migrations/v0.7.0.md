# Geurts Game Forge Documentation Migration to v0.7.0

**Version:** 0.7.0
**Status:** Approved migration guide
**Primary audience:** AI coding agents, automated migration systems, and Game Forge Intelligence
**Secondary audience:** Human developers
**Canonical path:** `Migrations/v0.7.0.md`

This guide migrates Unity projects from v0.4, v0.5, or v0.6 documentation integration to v0.7.0 without overwriting project-authored AI instructions or game design documentation.

---

## Target Architecture

The required result is:

```text
<ProjectRoot>/
├── GeurtsGameForgeDocumentation/
│   ├── AI_READ_FIRST.md
│   ├── GeurtsTechniqueManifest.md
│   └── GeurtsTechniques/
└── Docs/
    └── GameDesign/
        ├── GameDesignManifest.md
        └── project-specific design documents
```

The synchronized documentation directory and project GDD directory are separate authority domains.

---

## Historical Legacy Path Notice

The following path is shown only to identify and retire a historical, non-operational v0.5 synchronization layout:

```text
<ProjectRoot>/.geurts/upstream/
```

It is not a valid v0.7.0 bootstrap, fallback, cache, or AI entry route. Do not recreate it, restore it, or direct an AI agent to it.

---

## Before Migration

1. Commit or otherwise back up the Unity project.
2. Close or pause Unity/editor processes that may lock documentation or native entry files.
3. Preserve copies of these user-sensitive targets when they exist:

   ```text
   AGENTS.md
   .github/copilot-instructions.md
   .github/instructions/geurts-unity.instructions.md
   .github/instructions/geurts-game-design.instructions.md
   Docs/GameDesign/
   ```

4. Preserve the entire historical synchronized copy until the new visible copy is installed and validated.
5. Install the v0.7.0 `Tools/`, templates, migration catalog, and repository configuration supplied by Game Forge Intelligence or the package source.
6. Confirm Git and authenticated access to the private canonical repository are available. Do not place credentials in project files or command output.

A migration must stop before destructive replacement when a required backup cannot be created.

---

## Native Entry Migration Rules

Historical projects can contain these states:

- **v0.4:** native entries directly reference technique files under the old `Docs` layout.
- **Fresh v0.5:** `AGENTS.md` uses the historical hidden synchronization route while the three Copilot templates may still contain v0.4 direct-`Docs` content.
- **v0.4 upgraded to v0.5:** all native entries may remain v0.4 because the old setup copied only missing files.
- **v0.6:** native entries route through `GeurtsGameForgeDocumentation/AI_READ_FIRST.md`, but the setup still copied only missing files and could preserve older content.

The v0.7.0 manager must classify every target as fully managed, partially managed, user-owned, exact legacy, or modified legacy before mutation.

- Exact known legacy content may be backed up and migrated using `Tools/NativeEntryMigrationCatalog.json`.
- Partially managed files update only the explicit managed region.
- User-authored content outside managed markers is preserved.
- Modified legacy files without trustworthy markers are preserved and reported conflicted.
- `GEURTS-MANAGED-OPT-OUT` prevents managed updating and produces a skipped result.
- A backup failure prevents replacement.

Run the v0.7.0 AI setup workflow and review its created, updated, preserved, skipped, and conflicted report. Resolve conflicts explicitly; do not force replacement merely to complete setup.

Every successfully managed native entry must route through:

```text
GeurtsGameForgeDocumentation/AI_READ_FIRST.md
```

## Synchronize and Validate

From `<ProjectRoot>`, use the v0.7.0 bootstrap modes in this order:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Tools/BootstrapGeurtsInstructions.ps1 -Mode Check
powershell -NoProfile -ExecutionPolicy Bypass -File Tools/BootstrapGeurtsInstructions.ps1 -Mode Update
powershell -NoProfile -ExecutionPolicy Bypass -File Tools/BootstrapGeurtsInstructions.ps1 -Mode Validate
```

Requirements:

1. `Check` reports `CURRENT`, `UPDATE_AVAILABLE`, or `NOT_INSTALLED`, or exits with a categorized failure.
2. `Update` stages and validates the candidate before replacing the active copy, then reports `UPDATED` and the exact commit.
3. `Validate` reports `VALID` without contacting GitHub.
4. Authentication, network, remote, checkout, validation, conflict, file-lock, filesystem, and unknown failures remain distinct.
5. Any failed update preserves the previous valid synchronized copy.

Do not continue to cleanup unless `Validate` succeeds.

## Verify the Visible Copy

Confirm `GeurtsGameForgeDocumentation/` has exactly these three visible entries:

```text
AI_READ_FIRST.md
GeurtsTechniqueManifest.md
GeurtsTechniques/
```

Then confirm:

- `AI_READ_FIRST.md` and the manifest declare package v0.7.0.
- every synchronized manifest-listed file exists;
- `GeurtsTechniques/GeurtsFolderStructureDefinition.json` parses and declares definition/package v0.7.0;
- all native AI entry routes resolve to the visible entry point;
- the response-control technique remains v1.1 and chat-only;
- project GDD files remain under `Docs/GameDesign/` and were not copied into synchronized documentation;
- the exact synchronized commit is recorded for audit.

---

## Preserve and Initialize GDD Content

The v0.7.0 setup workflow may create only missing scaffolding:

```text
Docs/GameDesign/
Docs/GameDesign/README.md
Docs/GameDesign/GameDesignManifest.md
```

It must not overwrite an existing file. It must not invent mechanics, narrative, balance values, progression, characters, or other project facts. Existing project-specific GDD content remains authoritative.

After scaffolding validation, run the deterministic GDD manifest maintainer. Review added, removed, renamed, moved, imported, unclassified, unsupported, and conflicted results. Resolve duplicate identifiers and ambiguous renames before player-facing implementation depends on the affected documents.

---

## Retire the Historical Copy

Cleanup is a deliberate final migration action, never an automatic folder-definition action.

Only after the visible copy and native entries have passed validation:

1. Confirm no current script, package setting, native entry, or Unity integration points to the historical legacy path shown earlier.
2. Retain a recoverable backup containing the old synchronized commit and any unexpected local files.
3. Remove only the historical `upstream` child from the legacy `.geurts` directory.
4. Do not remove the entire `.geurts` directory if another tool or user owns other content inside it.
5. Run v0.7.0 `Validate` again and inspect source-control changes.

If path ownership is unclear, preserve the directory and report it for manual review. The presence of an obsolete path never grants automatic deletion authority.

---

## Rollback

If the migration fails:

1. Preserve all diagnostic output and categorized error information without credentials.
2. Restore the last validated visible synchronized copy from the bootstrap rollback state.
3. Restore any native entry only from its reported backup when the user-authored state is understood.
4. Leave project GDD content untouched.
5. Do not reactivate the historical hidden route; fix authentication, network, checkout, validation, conflict, or file-lock causes and retry v0.7.0 synchronization.
